# Security tool executor images

The executor image is untrusted code and runs with no Linux capabilities, a read-only root filesystem, an isolated workspace, strict resource limits, and no network by default. Build it from `services/security-runner/toolbox.Dockerfile`; build the separate firewall helper from `services/security-runner/guard.Dockerfile`. Reviewed amd64 base digests, the Debian snapshot, provider release checksums, and the reviewed Solidity compiler are recorded in `services/security-runner/toolbox-build.env`. CI builds both images from that lock, executes their offline smoke checks, and scans the four security images for vulnerabilities, secrets, and misconfiguration.

Both recipes require an operator-supplied `repository@sha256:<digest>` base image and a frozen Debian snapshot. The toolbox build also requires reviewed release versions and SHA-256 values for Gobuster, Foundry, and `solc`. The build never runs inside a tool job. It installs a bounded wordlist set and validates dependency and binary presence with `toolbox_smoke.py`.

After building, publish the artifacts to the approved registry and set `SECURITY_SANDBOX_IMAGE` and `SECURITY_GUARD_IMAGE` to their immutable repository digests. The runner never pulls or installs executor images. Run `scripts/scan-security-images.ps1` against the four final service and executor image digests; it requires local images, Trivy, and Docker, scans each image, and runs offline imports and toolbox/guard smoke checks.

## Egress enablement

The runner remains offline until the operator provides a guard digest, a dedicated Docker bridge named by `SECURITY_EGRESS_NETWORK` with label `com.blackonyx.security-egress=true`, and `SECURITY_EGRESS_VERIFIED=true`. The runner itself is not attached to that bridge. A per-job guard joins it, installs a default-deny nftables policy, and only then allows the untrusted toolbox to share that network namespace. Lab networks must be internal Docker networks labeled `com.blackonyx.security-lab-profile=<registered profile id>`; `SECURITY_LAB_PROFILES_JSON` binds each id to its network, private CIDRs, and TCP ports.

`SECURITY_EGRESS_VERIFIED` and `SECURITY_CAPTURE_VERIFIED` are independent operator attestations. Keep them false until independent observers have completed the documented DNS, redirect, direct-IP, IPv6, UDP, metadata, host-gateway, concurrent-job, guard-failure, cancellation, restart, and cleanup tests. The code checks local image/network readiness, but that check does not replace those escape tests.

For Kubernetes ingress enforcement, run `scripts/test-networkpolicy-enforcement.ps1` against the enforcing cluster with a digest-pinned Python probe image. It starts a temporary target selected by the configured destination `app` label, confirms the allowed namespace/app can connect, then proves an otherwise matching app label from a different namespace is denied. Repeat it for each real source selector and destination port in the Helm policy graph. A failed positive control means the result is inconclusive; a passed source-code or Helm render check does not establish CNI enforcement.

## Challenge providers

The gateway includes a persistent, actor-scoped `reference-basic` checker. It compares the bounded answer `flag{black_onyx_reference}` as text and never executes submissions. External providers are configured by fixed challenge ID, endpoint URLs, and exact IPv4 address pins in `SECURITY_CHALLENGE_PROVIDERS_JSON`; requests cannot supply URLs. Provider responses are capped at 64 KiB, redirects are rejected, and DNS must continue to resolve only to the registered addresses. Public provider endpoints must use HTTPS. The registry contract is [challenge_provider_registry.schema.json](../contracts/security-tools/challenge_provider_registry.schema.json).

`cast_send` is gated separately by `ENABLE_CAST_SEND` and verified egress. It accepts only a literal private IPv4 endpoint on TCP 8545 within an operator-registered internal lab profile, and the preview binds sender, recipient, calldata, value, endpoint, and resolved target. The read-only toolbox helper requires the `web3_clientVersion` method, chain ID 31337, and the requested sender in `eth_accounts`; it sends `eth_sendTransaction` and waits for a successful receipt. The Anvil node signs with its own unlocked test account. The gateway, runner, and toolbox receive no private key or mnemonic.
