## Recommended approach

Build a **hybrid anomaly-detection system with three compact Transformer encoders**, rather than forcing one generic BERT to understand system logs, source code, CPU charts, and network flows simultaneously. That “one model for everything” idea is attractive right up until it produces one mysterious anomaly score and nobody knows whether the server is compromised or merely running a backup.

Use:

1. **LogBERT-style encoder** for application and system logs.
2. **CodeBERT-style encoder** for source-code changes.
3. **Small tabular/sequence Transformer** for network flows and server metrics.
4. A lightweight fusion layer that combines their anomaly scores and shared context.

BERT-style models are particularly suitable for logs because they can learn the expected sequence of events using masked-token prediction. LogBERT and LAnoBERT both demonstrate self-supervised log anomaly detection using variations of masked language modeling, including training primarily on normal data. ([arXiv][1])

## Reference architecture

```text
                       ┌─────────────────────────┐
System/application logs│ Fluent Bit / Vector     │
                       └────────────┬────────────┘
                                    │
                                    ▼
                         Drain3 template parser
                                    │
                                    ▼
                         Tiny LogBERT encoder
                                    │
                                    ├── log anomaly score
                                    │
OpenTelemetry metrics/traces ───────┼── correlation metadata
                                    │
Zeek network-flow logs ─────────────┤
                                    ▼
                        Flow/metric Transformer
                                    │
                                    ├── traffic anomaly score
                                    │
Git commits / changed functions ────┤
                                    ▼
                          Small CodeBERT encoder
                                    │
                                    ├── code-risk score
                                    ▼
                         Score fusion + rules
                                    │
                     ┌──────────────┴──────────────┐
                     ▼                             ▼
              Alert/dashboard             Incident evidence
```

OpenTelemetry gives you a vendor-neutral collection layer for logs, metrics, and traces, including correlation through trace and span identifiers. ([OpenTelemetry][2])

For network monitoring, Zeek is a strong front end because it converts packet traffic into structured, semantically useful transaction logs. Its output includes fields suitable for investigation and machine-learning pipelines without requiring the model to ingest raw packet bytes. ([Zeek Documentation][3])

# 1. Server and application-log model

> **Status:** Design history. Substantial content is now **implemented** in the monorepo. Prefer `README.md`, `ANOMALY_DETECTION_PLATFORM.md`, and `docs/operations/` for current behavior. See [`docs_implemented/README.md`](README.md).


## Data preparation

Collect:

* `systemd` journal and syslog
* authentication logs
* kernel logs
* application logs
* container and Kubernetes logs
* database and reverse-proxy logs
* deployment events
* optional OpenTelemetry trace IDs

Remove or normalize highly variable values:

```text
Raw:
2026-07-26 13:41:02 Failed login for user alice from 10.0.4.21

Normalized:
Failed login for user <*> from <IP>
```

A streaming parser such as **Drain3** turns log messages into templates and template IDs. Drain3 specifically recommends separating structured fields such as timestamps, hostnames, and severity from the unstructured message before template mining. ([GitHub][4])

Example event sequence:

```text
[AUTH_START, USER_LOOKUP, PASSWORD_FAILURE, PASSWORD_FAILURE, ACCOUNT_LOCK]
```

This is generally better than treating every IP address, UUID, timestamp, and request ID as natural-language vocabulary. Otherwise the model spends its limited silicon intellect memorizing identifiers that were designed to be unique.

## Model objective

Train a small bidirectional Transformer using two tasks.

### Masked event prediction

Mask one or more events:

```text
[AUTH_START, USER_LOOKUP, MASK, ACCOUNT_LOCK]
```

The model predicts:

```text
PASSWORD_FAILURE
```

A high masked-token loss means the event is surprising in context.

### Sequence anomaly objective

Train the model to distinguish:

```text
Normal:
[SERVICE_START, CONFIG_LOAD, LISTENER_READY]

Corrupted:
[SERVICE_START, PRIVILEGE_CHANGE, LISTENER_READY]
```

Corrupted examples can be generated by:

* replacing an event
* changing event order
* duplicating rare events
* deleting required events
* inserting events from another service
* modifying parameter categories

LogBERT uses self-supervised objectives to learn normal log-sequence patterns and detect deviations from those patterns. ([arXiv][1])

## Suggested tiny configuration

Do not begin with full `bert-base`. Use something closer to:

```yaml
hidden_size: 256
layers: 4
attention_heads: 4
intermediate_size: 512
max_sequence_length: 128
vocabulary: 2,000-20,000 log templates
dropout: 0.1
```

That should land around several million parameters rather than BERT-base territory.

A useful alternative is a compressed architecture inspired by DistilBERT, which reduces the depth of the original BERT-style encoder while retaining the same general bidirectional Transformer structure. ([Hugging Face][5])

## Anomaly score

A practical score is:

```text
score =
    0.50 × masked_event_loss
  + 0.25 × rare_template_score
  + 0.15 × sequence_embedding_distance
  + 0.10 × parameter_anomaly_score
```

The embedding-distance component can be calculated against a centroid or nearest-neighbor index of known-normal sequences.

# 2. Source-code monitoring

Code monitoring is a different problem from runtime-log monitoring. Do not continually rescan the entire repository as one enormous text document. Analyze **changes**:

* changed functions
* commit diffs
* modified dependencies
* newly introduced API calls
* permissions and infrastructure changes
* configuration-file changes
* generated-code changes

## Model

Start from CodeBERT or distill it into a smaller student model. CodeBERT was pretrained jointly on programming language and natural language and supports downstream code-understanding tasks. ([arXiv][6])

Input example:

```text
[LANG=python]
[FILE=auth/session.py]
[DIFF]
- subprocess.run(command, shell=False)
+ subprocess.run(user_input, shell=True)
```

Classification heads could predict:

* unusual relative to repository history
* likely security-sensitive
* new external communication
* authentication or authorization change
* dangerous API introduction
* secret or credential handling
* dependency risk
* general defect probability

## Important limitation

A CodeBERT classifier should **augment**, not replace:

* Semgrep
* CodeQL
* compiler warnings
* dependency scanners
* secret scanners
* traditional static analysis

Code-only sequence models can overlook syntax, control flow, and data dependencies. Research combining code-language models with code-property graphs exists precisely because raw token sequences do not capture every program property. ([arXiv][7])

For a first release, use static-analysis findings as additional structured features:

```json
{
  "codebert_score": 0.76,
  "new_dangerous_api": true,
  "semgrep_findings": 2,
  "dependency_change": false,
  "author_baseline_distance": 0.43
}
```

This is substantially more reliable than asking CodeBERT to gaze into a function and divine all future CVEs.

# 3. Network-traffic model

## Prefer flows over raw packets

Use Zeek, NetFlow, IPFIX, or another flow exporter to produce events such as:

```json
{
  "source_role": "frontend",
  "destination_role": "database",
  "protocol": "tcp",
  "service": "postgres",
  "duration_bucket": 4,
  "bytes_out_bucket": 7,
  "bytes_in_bucket": 3,
  "connection_state": "SF",
  "hour_bucket": 2,
  "destination_seen_before": false
}
```

Do not feed raw IP addresses as ordinary tokens. Instead represent:

* subnet or zone
* asset role
* internal versus external
* country or ASN category where legally appropriate
* service
* port bucket
* byte-count bucket
* duration bucket
* connection state
* TLS characteristics
* DNS-query category
* whether the peer is new for that asset

## Small Transformer structure

Treat each connection as an event token with categorical and numerical embeddings:

```text
event_embedding =
    protocol_embedding
  + service_embedding
  + source_role_embedding
  + destination_role_embedding
  + numeric_projection
  + time_embedding
```

Feed 32–256 consecutive flow events per host or workload into a 3–4-layer Transformer.

Self-supervised tasks:

* predict the masked service or destination role
* predict the next connection category
* reconstruct bucketed numerical features
* contrast normal windows against corrupted windows
* detect whether a destination is contextually unusual
* predict communication edges between system components

The FlowTransformer framework explores Transformer-based intrusion detection over network-flow data, while Network Transformer research demonstrates self-supervised anomaly detection that incorporates communication topology for interpretability. ([arXiv][8])

For initial experiments, CICIDS2017 provides benign and attack traffic in both packet and flow-oriented forms, although production data from your own environment will matter much more for baseline behavior.

# 4. Metrics and resource anomalies

CPU, memory, latency, disk, and request-rate data are numerical time series. A text BERT tokenizer is not the natural choice here.

Use either:

* a very small Transformer encoder over numerical windows
* an autoencoder
* an Isolation Forest baseline
* Seasonal Hybrid ESD
* a forecasting model that scores prediction error

Input window:

```text
[
  CPU,
  memory,
  disk_io,
  network_io,
  request_rate,
  error_rate,
  p50_latency,
  p95_latency,
  queue_depth
] × previous 60 intervals
```

A two- or three-layer Transformer with a hidden size of 64–128 is usually enough to begin.

Metrics should also be available to the fusion model. A suspicious log sequence accompanied by a CPU spike, error-rate increase, and unusual outbound destination deserves a much higher priority than any of those signals alone.

# 5. Fusion and correlation

Each specialist produces a calibrated score:

```json
{
  "timestamp": "2026-07-26T20:41:00Z",
  "asset": "payments-api-03",
  "log_score": 0.91,
  "metric_score": 0.72,
  "network_score": 0.88,
  "recent_code_change_score": 0.63
}
```

The first fusion model should be simple:

```text
risk =
  logistic_regression(
    log_score,
    metric_score,
    network_score,
    code_score,
    deployment_age,
    asset_criticality,
    number_of_affected_hosts
  )
```

Do not immediately build another giant neural network. Logistic regression or gradient-boosted trees will make it much easier to understand why an incident was raised.

Example correlation rule:

```text
IF log_score > 0.80
AND network_score > 0.75
AND deployment occurred within 30 minutes
THEN severity = high
```

Preserve evidence:

```json
{
  "reason": [
    "unexpected authentication event sequence",
    "first outbound connection to destination category",
    "error rate increased 4.1 standard deviations",
    "authentication code changed 12 minutes earlier"
  ]
}
```

This evidence is often more valuable operationally than squeezing another decimal point out of benchmark F1.

# 6. Training strategy

## Begin with normal-only learning

Use a clean baseline period containing:

* normal weekday and weekend traffic
* deployments
* backups
* maintenance
* traffic peaks
* autoscaling
* certificate rotation
* expected failure and retry behavior

Reserve later periods for validation and testing. Do not randomly split individual events, because events from the same incident or session can leak across splits.

Recommended split:

```text
Weeks 1–4: training
Week 5: validation
Week 6: test
```

Also test on:

* a new software release
* a changed traffic level
* a new host or service
* simulated incidents
* red-team traffic
* previously unseen error templates

Log patterns drift over time, so a production system needs drift detection and controlled retraining rather than assuming that last quarter’s behavior is the eternal definition of normal. ([arXiv][9])

## Human feedback loop

Store analyst dispositions:

```text
true_positive
false_positive
expected_change
maintenance
unknown
```

Use these later to:

* calibrate thresholds
* train a small supervised classification head
* suppress known maintenance patterns
* find weak areas in the telemetry
* identify model drift

Do not automatically retrain on every event marked normal. A compromised event misclassified by an analyst should not become part of the model’s sacred definition of healthy behavior.

# 7. Evaluation

Track these separately:

* event-level precision, recall, and F1
* incident-level recall
* false alerts per host per day
* average detection delay
* percentage of alerts with useful evidence
* performance on unseen anomaly types
* performance after deployments
* CPU and memory consumption
* inference latency
* analyst-confirmed usefulness

The most important production metric is often:

```text
actionable true incidents / total alerts
```

A model with impressive academic recall and 800 alerts per shift is merely an automated workplace-hostility system.

Public log benchmarks are available through LogHub, including labeled HDFS and BGL datasets. ([GitHub][10])

Use those to verify the implementation, but tune thresholds using your own environment.

# 8. Deployment footprint

A realistic initial deployment:

```text
Log encoder:
  4 layers, hidden 256
  5–15 million parameters

Network encoder:
  3 layers, hidden 128
  1–5 million parameters

Metric encoder:
  2 layers, hidden 64
  under 1 million parameters

Code model:
  distilled or fine-tuned CodeBERT derivative
  run in CI, not continuously on every server
```

The runtime models can run centrally on CPU in batches. The code model can run only when a pull request or commit changes.

Export models to ONNX and apply dynamic INT8 quantization. ONNX Runtime provides Transformer-oriented preprocessing and quantization support, while Hugging Face Optimum supplies wrappers for ONNX Runtime quantization. ([ONNX Runtime][11])

Keep collection agents lightweight. The server should export telemetry, not run four neural networks beside the production database like some sort of self-inflicted denial-of-service experiment.

# 9. Practical MVP

## Phase 1: logs only

Implement:

```text
Fluent Bit or Vector
        ↓
Drain3
        ↓
Kafka or simple queue
        ↓
Tiny LogBERT
        ↓
PostgreSQL/OpenSearch
        ↓
Alertmanager/dashboard
```

Train on four to eight weeks of largely normal logs.

Output:

```json
{
  "score": 0.94,
  "service": "payments",
  "sequence": [
    "request_received",
    "credential_lookup",
    "unexpected_privilege_change",
    "external_connection"
  ],
  "top_unexpected_events": [
    "unexpected_privilege_change"
  ]
}
```

## Phase 2: add network context

Install Zeek at the relevant network boundary, ingest `conn`, DNS, HTTP, and TLS-related records, and train the small flow Transformer.

## Phase 3: add CI code analysis

Analyze changed functions with a distilled CodeBERT classifier and combine its output with conventional scanner findings.

## Phase 4: correlate signals

Use OpenTelemetry resource attributes, trace IDs, service names, deployment versions, host IDs, and Kubernetes metadata to connect the events.

---

## Final recommendation

The best starting design is:

```text
Drain3 + 4-layer LogBERT
Zeek + 3-layer flow Transformer
OpenTelemetry for correlation
CodeBERT only in CI
simple logistic-regression fusion
ONNX INT8 inference
```

Build the **log model first**. Logs have the strongest fit with BERT’s masked-language objective, LogBERT implementations and benchmark datasets already exist, and the model can learn from mostly normal data. The official LogBERT repository includes the full process of parsing raw logs, constructing sequences, and training the model, making it the most direct implementation reference. ([GitHub][12])

Do not force server metrics into textual BERT tokens, do not train directly on raw packet payloads for the first version, and do not rely on a code-language model as the sole vulnerability scanner. A compact specialist ensemble will be smaller, easier to debug, and considerably less likely to become an expensive machine for declaring Tuesday anomalous.
